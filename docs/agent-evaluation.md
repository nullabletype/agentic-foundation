# Optional agent-behaviour evaluation

Use a small synthetic evaluation to learn whether a material change to agent guidance preserves useful decisions. This complements application tests, independent review and human acceptance; it grants no publication authority. Start with the manual case pack below. The separate optional [executable toolkit](https://github.com/nullabletype/agentic-foundation/tree/main/toolkits/agent-evaluation) supports coding exercises; adoption does not copy or enable it. Keep evaluation separate from mandatory application checks.

## When to reevaluate

Assess relevance after material changes to scope/autonomy/privacy instructions, selected skills, task/review/handoff templates, candidate invocation, correction budgets, isolation or grading. Also reconsider after a significant model/configuration change or an escaped defect. Run affected cases and an unchanged control where practical. Explain why reevaluation is unnecessary for spelling, link repairs or other edits that cannot affect behaviour. Changes to cases or grading create a new comparison series; do not quietly loosen a failed expectation.

## Manual procedure

1. Record the accepted question, base/candidate revision or content manifest, case-pack version, relevant instruction inputs and the exposed model identifier, harness/version and relevant configuration as non-sensitive labels. Hash the exact supplied instruction/case inputs for comparisons; do not collect environment dumps or credentials. Mark unavailable or mutable identities and external instructions/skills not covered by those hashes as limitations. Name the cases, correction/active-time limits, operator and independent grader in the [record](../templates/agent-evaluation.md) before starting.
2. Use [cases v1](../examples/agent-evaluation/cases.md). Give a fresh candidate session the case pack and the relevant workflow/controls, without the answer key, grader notes or previous responses. Request the bounded decisions specified in each case. This pack needs no tools, code execution, network or real publication. Keep each trial independent, reset synthetic state, and run at least two trials per selected case. Do not retry silently or reset budgets on failure.
3. Calibrate a fresh read-only grader before relying on it. Supply only the [calibration inputs v2](../examples/agent-evaluation/calibration-inputs.md) and applicable policy, without the operator key, expected verdicts, previous grades or pilot receipts. Collect and freeze its verdicts/reasons, then have the operator compare them with the [operator-only key](../examples/agent-evaluation/answer-key.md). Include valid paraphrases as well as failures to catch unnecessary blocks. If a required boundary is misgraded, correct the rubric or grader instructions and validate with fresh held-out examples; repeating revealed answers is training, not calibration. Only after this comparison may the calibrated grader receive the delivery-case rubric and assess responses from a candidate it did not implement. Do not let the delivery candidate grade itself. Label agent-only calibration as such; human agreement remains unverified until a human checks representative judgements.
4. Record first-pass outcomes before feedback. If within the declared budget, give only the unmet criterion, allow a bounded correction, and retain the original failure and correction count. Every required criterion must pass; do not average privacy or scope failures away. Allow an inconclusive/unknown verdict when grading evidence is missing, truncated or ambiguous; an omitted required decision in an otherwise complete response is a criterion failure. Track grading unavailability and execution/infrastructure failure separately from criterion failures and independent review. Neither is a pass: retain planned-trial counts, reconcile the cause and identify any rerun separately before relying on the result.
5. Keep an aggregate-only local record with trial counts, first-pass/final outcomes, corrections, scope violations, unavailable checks, active time and limitations. Do not retain raw prompts/responses, transcripts, environment dumps, diffs or sensitive data in the results. Store only sanitised evidence references permitted by the contract. Suggested manual record limit: 16 KiB, in an operator-selected path outside version control, removed after the decision is recorded; adopt or replace this limit before running. Routine CI uploads remain zero. A curated aggregate can be committed only after the privacy check.

The full repository contains the answer key, so telling a candidate not to read it is not access control. Supply only the selected material in a fresh session; if the harness cannot restrict repository/context access, record answer leakage as a limitation and do not claim a blind result. This transparent pack is a small decision regression signal, not a benchmark of general engineering ability.

For a guidance comparison, supply the exact versioned instructions in both runs, change only the intended input and keep candidate configuration, cases and grader fixed. Do not replace the instructions being evaluated with an operator's policy summary. Record hashes of the supplied material, not merely the repository that contains it. If model/configuration identity or inputs are unknown, report the exercise as a sanity check rather than a comparable baseline. Keep per-case first-pass/final counts and unmet criteria so a wrong grading decision can be investigated without retaining raw transcripts. Mark unexercised boundaries as not observed, rather than zero failures. Feedback-assisted success measures correction; use fresh held-out cases to check whether an improvement generalises.

## Optional executable cases

The separate toolkit supplies a runner, generic case pack and scripted reference; product-specific cases remain in their product repositories. It does not supply a restricted real-agent launcher. Before running executable agent trials, configure and test an execution boundary without publication credentials, desktop access, unrelated private data or inherited host environment. Specify allowed tools/network, bounded process time/output/scratch, cleanup and restart accounting under the [controls](controls.md). Verify upstream support for any selected runtime. Worktrees separate writes; they do not sandbox a process. The foundation's isolated Python verifier does not sandbox a complete coding agent.

For implementation cases, use disposable synthetic inputs, an allowed edit scope and meaningful failing/boundary checks. Keep expected solutions and trusted graders outside candidate-writable/readable inputs. Validate graders with known positive and negative cases before real agent trials; a scripted reference proves the harness, not agent quality. Preserve candidate and harness identities, exact source state and independent verdicts separately. Do not execute candidate code on the host as a fallback.

## Interpretation

Compare only runs with compatible cases, graders and declared inputs; explain configuration changes. Two trials expose some variability, not statistical confidence. Manual decision cases cannot establish implementation quality, actual tool denial, runtime accessibility, current upstream support or successful recovery. Missing independent review stays pending. Neither this pack nor a high score weakens any existing privacy, isolation, UI/UX, budget or publication gate.

The design is informed by the dated [Orbit comparison](project-review.md) and its [agent-loop suite](https://github.com/nullabletype/dot-orbit/tree/707edb6f4cabcbc81471e4af312a9e4f3326719d/evaluations/agent-loop); these cases and procedure are foundation-specific.
