Source inspection on **17 October 2026**, comparing the foundation's [previous review](project-review.md) of Orbit at `4d464fed486841da02eaec9d70d277f0f8afb055` with local Orbit HEAD `707edb6f4cabcbc81471e4af312a9e4f3326719d`. Foundation baseline: `b76ed6da761a0a8f339634b5f5331427de826f3c`. Both checkouts were initially clean. Remote freshness, live GitHub settings, hosted runs and current upstream dependency support were not verified. No Orbit commands or application were run and no capture tools were used. The findings below are recommendations, not adopted policy or implemented enforcement.

### Evaluate changes to the agent setup

Orbit now has six synthetic cases covering specification boundaries, bounded implementation, regression repair, documentation drift, accessibility verification and dependency review. Each has allowed paths, observable checks and a rubric; every required check must pass. The runbook explicitly triggers reevaluation for material changes to instructions, skills, templates, orchestration and graders. It separates a scripted reference run that tests the harness from a real agent baseline. See the [evaluation runbook](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/evaluations/agent-loop/README.md).

The retained [3 October baseline](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/evaluations/agent-loop/baselines/2026-10-03-codex-gpt-5.5.json) records 12/12 successful trials after four corrections, with 8/12 first-pass successes and independent review unavailable for all 12. Its evaluated commit is `60365242b3e10af7912b93f812752e3d615c61c6`, not current HEAD. This is useful historical evidence, not proof that today's setup performs equally well or that independent review occurred.

The foundation already has [reviewer calibration](automation.md#calibrate-the-reviewer) and tool regression tests. The gap is evaluating how the delivery agent behaves after its instructions change. Start with a few foundation-specific cases: stale publication evidence, a dependency reopened after readiness, an out-of-scope edit, an instruction to capture a native window, and a missing or unknown support result. Record the source revision, instruction/harness fingerprints and non-sensitive candidate configuration alongside first-pass success, correction count, scope violations, unavailable checks and false approvals; do not hide a required failure in an average score. Keep expected answers out of the candidate's accessible inputs.

Adapt the design rather than copying the runner. Orbit's [harness](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/evaluations/agent-loop/harness.mjs) uses temporary worktrees, host processes and inherited environment values. A worktree separates writes but does not enforce credential, network or desktop isolation. Foundation [execution controls](controls.md#verification-and-independence) remain stronger. Its existing Linux verifier supports small Python candidates, not a complete coding agent; a real agent evaluation needs a separately configured execution boundary. Any adopted runtime also needs a fresh upstream support check. Preserve bounded output and storage, aggregate-only records and zero routine artifact uploads.

Also keep grader limitations visible: Orbit's trial pass reflects deterministic checks, while candidate process failures and reviewer verdicts are recorded separately. Its transparent fixtures and available reference solution do not test resistance to benchmark gaming. A foundation evaluation should distinguish check success, execution failure and independent acceptance, and validate the graders with known failing cases before comparing instruction quality.

### Admit tasks deliberately

Orbit's [readiness contract](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/docs/agents/issue-tracker.md) now starts proposals in triage. A maintainer admits an issue to dependency automation; manual states and unrelated issues remain outside it. Dependencies have one canonical field. Malformed contracts, missing dependencies and cycles return the issue to triage; reopened dependencies restore blocking. The [implementation](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/.github/scripts/issue-readiness.mjs) plans targeted label changes, and its [workflow](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/.github/workflows/issue-readiness.yml) offers a read-only dry run.

The foundation already requires an accepted contract, satisfied dependencies and no material open decisions. Clarify two distinctions in the existing task/workflow guidance: submitting structured text does not approve scope; closing a dependency does not prove its acceptance or integration. Orbit mechanically checks closure, so any future reusable readiness tool must document that limitation. Do not require its exact labels, GitHub Project or Node implementation. Add automation only when maintaining the queue has become a demonstrated cost, with explicit admission, manual override, dry run and negative tests.

### Map acceptance to evidence

Orbit's [PR template](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/.github/PULL_REQUEST_TEMPLATE.md) adds an acceptance-criterion/evidence table and explicit accessibility and dependency impact. Its [definition of done](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/docs/development/definition-of-done.md) names keyboard operation, accessible names/roles/states, focus and non-colour cues.

Foundation templates already collect commands, review and human approval, but an explicit mapping would make missing acceptance evidence easier to spot. Add the small table where it helps, reusing evidence references rather than duplicating logs. For interactive projects, name concrete accessibility outcomes in the task. Keep human approval and unavailable platform checks explicit; markup or headless tests alone cannot establish assistive-technology behaviour.

### Make safe review data easy to launch

Orbit's [sample workspace](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/docs/development/sample-workspace.md) is generated through production domain/store APIs, refuses destination collisions and supports a fixed date. It exercises empty, long-content, Unicode, ordering and date-boundary states without committing database bytes.

The transferable addition is a project-contract field for the synthetic launch command, data-generation command, scenario coverage, deterministic clock/seed where useful, and owned output limits/cleanup. Do not copy Orbit's screenshot use or normal-workspace launch escape hatch into agent verification. Its document has inconsistent wording about default-workspace generation; verify actual launch/generator implementation before adapting commands. Keep the sample separate from focused tests and migration fixtures.

### Strengthen security evidence without permanent upgrade churn

Orbit's [verification gate](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/tools/DotOrbit.Verification/VerificationGate.cs) adds direct/transitive vulnerability and deprecation audits. It parses the JSON report and checks expected schema, parameters, source and results rather than accepting process exit zero alone. Its [security controls](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/.github/scripts/security-controls.mjs) also check an explicit review deadline, approved package sources and upstream version drift.

Foundation [support policy](support-policy.md) already covers lifecycle evidence and transitive dependencies. Add reusable guidance for validating the scanner's actual results, rejecting malformed or incomplete reports, and assigning a dated recheck. Keep policy failures, unavailable upstream evidence and update notifications distinguishable. Orbit's drift checker fails when latest versions differ and rejects Node maintenance phase; neither condition alone proves an upstream-supported selected release is unusable under foundation policy. Do not import those stricter rules or the C# CodeQL workflow by default.

## Useful examples, not universal machinery

Orbit's [performance report](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/docs/development/performance-review.md) connects a symptom to synthetic workloads, exact commits and platform-specific measurements. It distinguishes cold observations from warm distributions and adds structural checks for prohibited full reads/rebuilds. Reuse that investigation method for performance work; do not copy its thresholds or infer Windows acceptance from Linux. Its opt-in recorder records timing metadata, not screen video, but foundation adoption should still use synthetic data and bounded diagnostics.

Orbit's [release controls](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/.github/scripts/release-controls.mjs) separate source admission, package smoke and draft preparation, including tag-to-commit checks and asset allowlists. Retain these as future adopter examples. The [workflow](https://github.com/nullabletype/dot-orbit/blob/707edb6f4cabcbc81471e4af312a9e4f3326719d/.github/workflows/release-packages.yml) now also uploads packages on main pushes and prepares tagged drafts; this is broader than the old review's manual-upload description. It supplies no new release authority here, and count/byte/retention limits still need explicit enforcement.

## What to retain unchanged

The foundation already has stronger mandatory independent verification, exact-candidate evidence, resumable budgets, privacy controls and separate merge/release authority. Orbit still describes independent review as practical/available and permits screenshots. Its existing multi-agent/model-routing guidance also predates the previous baseline; it is not a new lesson from this comparison. Keep delegation proportional to the task and maintain one writer per checkout.

The earlier [source-project recommendations](project-review.md#follow-up-candidates-for-the-source-projects) are historical: Orbit removed screenshot requests from its PR template and removed the stale first-issue sequence, but screenshot references remain elsewhere and mandatory independent review is still weaker. Preserve that dated record and use this supplement for the current comparison.

Recommended first implementation slice: add the acceptance/evidence mapping, clarify readiness admission, and document optional behavioural evaluation with its isolation and reevaluation requirements. Then pilot a few synthetic cases before selecting or building an agent runner. No broader permissions or weaker gates are proposed.

Orbit already has criterion/evidence mapping, a maintainer-controlled admission contract, reevaluation triggers and a retained first-pass/correction distinction. It does not need a duplicate manual evaluation pack. Its optional reviewer would benefit from the foundation's withheld-answer calibration, inconclusive verdict and held-out-after-coaching guidance. The retained baseline identifies an older evaluated commit, so it is historical evidence, not a current-HEAD result; verify any newer evidence before deciding a rerun is missing.

In the reverse direction, the foundation still has two useful, deliberately deferred Orbit lessons: a concrete synthetic review launch/data-generation contract, and security checks that validate structured scanner results rather than exit status alone. These remain worthwhile small adopter-facing additions; the foundation does not need Orbit's application stack, permissive capture policy or host-based evaluation runner.
